# Changelog

## [1.0.2] - 1405-08-19

Round-2 through round-16 review fixes (all unpublished; one release).

### Fixed

- Round 16, two P1s of the round-15 async seam: (1) the rejection containment landed in a MICROTASK while the parser's stop-guards are synchronous — the remaining deltas of the SAME chunk dispatched before the flag was seen (probe: three calls, three rejections, versus exactly one for a sync throw). Deliveries are SERIALIZED through a settlement chain now: each delta reaches the handler only after the previous result settled, a rejection stops every later queued delivery at its chain step, and the handler-stop flags land through the same path for both throw and rejection (test locks the real CALL COUNT on a three-delta single chunk — the round-15 test only asserted the caller-side array, which was vacuous). (2) The flush-path re-check read the flag synchronously, so an async rejection on the FLUSH-dispatched final delta leaked as `LLM_STREAM_INTERRUPTED` (a framing verdict on a handler bug — the same misreport the round-13 sync fix closed); the done path now awaits the delivery chain before re-checking, and a test locks `LLM_REQUEST_FAILED` for the async flushed-delta shape (80 tests).
- Round 15 P1: an ASYNC receiving handler reports its failure as a rejected Promise, not a throw — the onText wrapper discarded the return value, so every rejection escaped as an unhandledRejection that KILLS the host process under Node's default mode while the transfer carried on delivering deltas and the stream reported `completed` (probe: four dispatches, four unowned rejections, ending completed). The wrapper now covers the return value (`Promise.resolve(...).catch(...)`) so a rejection takes the SAME handler-stop path as a throw — transfer stopped, no further delivery, `LLM_REQUEST_FAILED` (test locks the ending AND zero unhandled rejections); the settings `publish` call got the same containment. The manifest and the reference now state the async-handler semantics explicitly (78 tests).
- Round 14: the round-13 parser regression test was rewritten to the REAL mid-dispatch path — it set the handler-failed flag BY HAND before feeding, locking only the entry guard while the CHANGELOG claimed the three-delta scenario; the flag is now set by a service-shaped wrapper's catch and "exactly one delivery" is asserted on a three-delta chunk. And the handler-stop ending became CONTRACT, not just a CHANGELOG claim: the manifest's stream description, the reference's interrupted-endings list and the `LLM_REQUEST_FAILED` table row state the immediate stop, the no-further-delivery rule and the code, including a throw on the flush-dispatched final delta.
- Round 13: the receiving handler's failure now REACHES THE PARSER (`sink.handlerFailed` joins the decided-ending guards) — after a throw, the remaining events of the same chunk stop being parsed and delivered; cancel only reaches the transport, not the text still queued in the parser (test: a three-delta chunk whose first delta throws delivers exactly once). And the flush can be the FIRST dispatch of a buffered delta — the handler check re-runs after it, so a handler breaking on the flushed delta reports the documented `LLM_REQUEST_FAILED` instead of misreporting a framing fault (`LLM_STREAM_INTERRUPTED`) (gate test added). The SSE framing paragraph moved from the `complete` section (which sees no SSE) to `stream`, and the single-break fusion consequence is now stated in the contract, not only the CHANGELOG (77 tests).
- Round 12: the SSE processor moved from line-at-a-time parsing to the SPEC dispatch model — each event's `data:` fields accumulate and dispatch at the blank-line terminator (or the stream's normal close via the parser flush), so a provider breaking one JSON payload across SEVERAL `data:` lines is one readable event instead of an unreadable stream; empty data fields stay ignored (separator noise), a payload broken mid-string-literal is still honestly refused, and single-`\n` separated streams fuse per the spec and refuse if the fusion is not valid JSON (two parser tests; the two old streams whose shapes were per-line-lenient now use the spec-correct blank-line separation). The parser gained an explicit `flush` (two synthetic line breaks settle a held CR, the buffered final line and the pending event — EOF is an event terminator), and the service calls it only AFTER every settlement guard: a deactivation landing in the settle window can no longer push a buffered text delta into the caller's handler after the plugin died (gate test locks the zero-delivery). The stream framing rules are documented in the reference (75 tests).
- Round 11: the SSE processor honors ALL THREE of the SSE spec's line separators (LF, CRLF and bare CR — a CR-only stream used to yield ZERO events, so even the end marker never landed), and a trailing lone CR is held across chunk boundaries so a CRLF split between chunks still splits correctly; a final event with NO trailing line break (minimal OpenAI-compatible proxies) is settled by one synthetic line break the done path feeds at a normal close — without it the end marker rotted in the parser buffer and a stream the provider closed normally reported as `LLM_STREAM_INTERRUPTED` (two tests). The round-10 unknown-finish-reason rule is now locked at the SERVICE wiring, not just the pure helper: a complete response with an unknown reason rejects `LLM_INVALID_RESPONSE`, and a stream event with one ends interrupted with the same code while text delivered before it stays with the caller (two tests; 72 total). And the round-10 baseUrl rule reached the contract documents: the manifest's `setSettings` description, the reference's Settings section and its `LLM_SETTINGS_INVALID` row, and the requirements' validation clause all state the no-query/no-fragment rule explicitly; the reference's Conversation section states the unknown-finish-reason fate too.
- The settings guard is now a DECLARED contract: `SERVICE_UNAVAILABLE` is listed in the manifest for `setSettings`, `clearSettings` and `getSettingsStatus`, and the reference documents it (plus the pre-activation allowance for the settings methods, which unlike the conversation methods stay usable between prepare and activate).
- The handler-error catch uses the shared defensive cancel too: a throwing cancel while stopping the transfer after a broken `onText` can no longer escape raw into the transport's read loop; deactivate's cleanup loop uses the same helper (gate test added for the combined failure).
- The rejection-window test now holds its rejection on a gate instead of a real timer (67 tests).
- Round 10: three silent-acceptance paths fail loudly now — a malformed `options.json` flag throws `LLM_INPUT_INVALID` like every other option (a silent "off" would hand the caller raw text instead of JSON); a PRESENT finish reason outside the declared set (a proxy's custom string, garbage) is an unreadable response — `LLM_INVALID_RESPONSE` in `complete`, the structured interrupted ending in `stream` — while absence still defaults to `stop`; and a base URL carrying a query string or fragment throws `LLM_SETTINGS_INVALID` at save time instead of swallowing `/chat/completions` into itself and sending every request to the wrong address (tests added).
- Round 8: the error table's `SERVICE_UNAVAILABLE` row now states the settings-methods exception (usable between prepare and activate) instead of contradicting the Settings section two pages above; that pre-activation allowance is locked by a dedicated service-level test (settings work, `complete` still refuses) so the guard can never silently harden (68 tests); the test names outside the `should_..._when_...` convention all moved into it (round 9 caught two leftovers: the round-8 window test's `while_` clause and a protocol chunk-boundary test); and the core-contract strings in `index.js` (`core:service-unavailable`, `REQUIRED_DEPENDENCY_LOST`, `REQUIRED_DEPENDENCY_UNAVAILABLE`) joined the plugin's constants module instead of staying magic literals.

- The transport's immediate rejections (address policy, validation) now cross the boundary through the delivery mapping (`LLM_REQUEST_FAILED`) instead of leaking undeclared `HTTP_*` codes.
- A deactivation landing while the transport was being resolved cancels the transfer right away, and a stream completing after deactivation reports the standard unavailable error instead of a fake completion.
- The dead `sink.text` accumulation (the answer text was kept for no reader) and the stale `PLUGIN_VERSION` constant are gone; `LLM_SETTINGS_INVALID` is no longer declared for `complete`/`stream` (only `setSettings` throws it); `lib/llm-protocol.js` is listed in the reference structure and exported like the other lib modules.
- The unified deactivate rule now covers the remaining windows: a transport REJECTION landing after deactivation reports the standard unavailable error (never the delivery-mapped code), the settings methods refuse after deactivation like every other method (no settings writes or events for a dead plugin), and every cancel path (cleanup loop, acquisition windows, returned handle) shares one defensive cancel so a throwing cancel never leaks raw (tests added for all three).
- One settlement rule now covers both methods uniformly: a settlement landing after deactivation reports the standard unavailable error whatever shape the transport ended in (provider status, delivery error, handler failure) — applied at the start of settlement handling in `complete` (thrown) and `stream` (interrupted shape, ahead of the handler-error branch); six gate tests lock the method × scenario matrix.
- The `completed` branch of `complete` now applies the same guard as `stream`: a completion landing after deactivation throws the standard unavailable error instead of returning an ordinary answer for a dead plugin (dedicated gate test added for both timings).
- `tests/llm-protocol.test.js` added: `buildOptions` boundaries, `classifyBadRequest` wording classes, `normalizeFinishReason` and the SSE parser's edge states (partial lines across chunks, empty `data:` lines, unreadable events, finish reason/usage).
- The immediate stream-rejection mapping and the Persian structure line in the reference are covered/cleaned; one test name moved to the `should_..._when_...` convention.

## [1.0.1] - 1405-08-15

### Fixed

- A provider error status on `stream` now maps to its categorized code (`LLM_UNAUTHORIZED`, `LLM_RATE_LIMITED`, …) instead of always reading as a mid-stream cut; the transport delivers non-2xx as an ordinary completed result and the mapping was only wired for `complete`.
- A throwing `onText` handler no longer escapes into the transport's read loop: the transfer stops and the stream ends interrupted with `LLM_REQUEST_FAILED`.
- `LLM_INPUT_INVALID` is declared in the manifest for both methods, closing the manifest/reference mismatch.
- The `core:service-unavailable` subscription is released on shutdown/deactivation (and on a repeated `prepare()`); a missing dependency at activation throws a structured startup error (`REQUIRED_DEPENDENCY_UNAVAILABLE`).
- The pure OpenAI-protocol helpers moved to `lib/llm-protocol.js` (service file down from ~595 lines); the transport stream-interrupted code lives in `constants.js`.

### Tests

- Test fakes replaced real timers with deterministic gates; new tests cover the stream status mapping, the handler-error path, the cancelled `complete` ending, the runtime dependency-loss critical report and the unsubscribe paths; per-source test files added (`error`, `constants`) and `tests/entry.test.js` renamed to `tests/index.test.js` (42 tests). The requirements doc now states explicitly that cancellation is the streaming handle's operation.

## [1.0.0] - 1405-08-13

Initial release: the single provider-facing LLM point for the chat/voice capability stack — in-memory user connection settings (base URL, model, optional key, never persisted, never exposed), OpenAI-compatible `complete` (full answer with finish reason and usage) and `stream` (progressive text through the shared flow pattern with three endings), native-JSON-mode option, minimal sampling options, SSE decoding with a streaming decoder (multi-byte characters survive chunk boundaries), categorized provider-error mapping (`LLM_UNAUTHORIZED`, `LLM_MODEL_NOT_FOUND`, `LLM_RATE_LIMITED`, `LLM_CONTEXT_TOO_LONG`, `LLM_JSON_UNSUPPORTED`, …), per-request settings snapshots, independent cancellation, and the `llm:settings-changed` event. Built on `pey.http` 2.0.0; `docs/requirements.md` (numbered pey format) is the construction source of truth.
